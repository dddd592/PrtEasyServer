PrtEasyServer v2.1.0 升级交付说明

突破「只支持 PCL / PostScript 打印机」的限制，并让客户端无需安装驱动

交付日期：2026-10-23 · 项目：Windows-PrtEasyServer（原生 C++ x64） · 全部 10 个源文件通过语法与严格警告检查

一、交付了什么

升级围绕一个核心判断展开：原版是「RAW 透传服务器」，不是「打印服务器」。它把「打印机型号支持」的责任完全推给客户端——客户端必须装厂商驱动并产出 PCL/PS 字节流。因此喷墨机、标签机、小票机全部不可用，macOS 与 iOS 也天然无法接入。

本次升级新增四项能力，全部保留原有「一台打印机一个端口」架构，现网配置不受影响：

1RENDER 模式

服务端用打印机自己的驱动渲染内容，突破型号天花板。

  • 通过 CreateDC("WINSPDC") 打开队列设备上下文，驱动负责最终语言转换
  • 文本自动换行与分页，CJK 可逐字断行
  • 图片按 真实物理尺寸放置（依图像 DPI 与打印机原生 DPI 换算），修复标签机打印缩小问题
  • 纸张、方向、份数经 DEVMODE 交给驱动处理
喷墨机标签机 小票机host-based 激光机

2HTTP 打印 API

客户端零驱动打印，手机、macOS、ERP、脚本都能直接用。

  • POST /api/print?printer=名称&paper=A4
  • 载荷类型自动识别：图片 / 文本 / PDF
  • 参数：printer copies paper orientation fit scale monochrome fontsize font
  • GET /api/printers 返回打印机列表 JSON
  • 内置网页已加入 API 说明与 curl 示例
iOS / AndroidmacOS ERP / 脚本

3mDNS 自动发现

打印机自己广播，客户端不再需要手输 IP。

  • 每台打印机以独立实例广播 _pdl-datastream._tcp.local
  • PTR / SRV / TXT / A 记录，TXT 携带 rp= 端口与队列名
  • 跟随服务器启停；5353 端口被占用时自动降级并写日志
零配置

4LPD 监听（RFC 1179）

兼容传统 Unix / 嵌入式 / 老旧设备客户端。

  • 队列名映射到已配置打印机，也可用打印机名
  • 支持 0x01 打印（带控制文件）、0x02 仅数据、0x03 队列状态、0x05 移除作业、0x06 队列列表
  • 设置页可开关，默认端口 515
默认关闭

三、质量保障

关键约束：本机没有 MSVC，也没有管理员权限。为了不让代码「写完就交、无法验证」，我下载了便携版 MinGW 工具链（WinLibs GCC 16.2.0）搭建了验证闭环。它抓出了 20 余处真实错误，包括 DMPAPER_LETTER_SMALL 宏名错误、std::atol 不支持 wchar_t、GDI+ C++ 包装类误用、DeviceCapabilitiesW 在两套 SDK 中第 5 参数类型不同（WORD vs DEVMODEW*）、GetLocalIPv4Address() 返回类型不匹配等。这些问题在 MSVC 下同样会失败。

检查结果

全量语法检查10/10 通过common / config / localization / lpd_server / main / main_window / mdns_broadcaster / print_api / printer_server / render_engine
严格警告检查0 警告-Wall -Wextra（排除 MSVC 专有 #pragma comment）
原有文件完整性已核对common.cpp 与 main.cpp 零改动；printer_server.cpp 仅删除 7 行被替换的旧逻辑
跨工具链兼容已处理GDI+ 调用统一走两套 SDK 共有的 flat API，差异用条件编译隔离
MSVC 实际编译未执行本机无 Visual Studio，需你在 x64 Native Tools 提示符中执行 build-windows10.cmd
真实打印机出纸未执行无物理打印机，须先用非关键设备试点
附带成果：tools/check_syntax.sh 让这个项目从此有了「无 Visual Studio 也能自查」的机制。它在临时副本里改写两处 MSVC 扩展语法（wstring 文件流），绝不改动交付源码，可随时接入 CI。

五、怎么用

方式一：把某台打印机切到 RENDER 模式

  1. 在设置页把该打印机的「打印模式」选为 RENDER，保存
  2. 客户端向该端口发送文本或图片即可，无需任何驱动

方式二：用 HTTP API（推荐）

# 打印文本（自动换行分页）
curl -X POST --data-binary @note.txt \
  "http://192.168.1.50/api/print?printer=HP%20LaserJet"

# 打印标签图，102x152 为毫米（4x6 英寸）
curl -X POST --data-binary @label.png \
  "http://192.168.1.50/api/print?printer=Zebra%20ZD220&paper=102x152"

# 查看可用打印机
curl "http://192.168.1.50/api/printers"

方式三：传统 LPD 客户端

lp -h 192.168.1.50 -P "HP LaserJet" /path/to/file

验证步骤

# 1. 编译（在 x64 Native Tools Command Prompt 中）
build-windows10.cmd

# 2. 启动服务器后跑冒烟测试
bash tools/smoke_test.sh 192.168.1.50 80
测试顺序建议：先用 Microsoft Print to PDF 虚拟队列验证渲染效果（改窗口、不浪费纸），确认无误后再切真实打印机出纸。冒烟脚本只报告服务端应答，不能证明纸真的出来了——这是打印服务器测试的固有陷阱。

六、PDFium 依赖（后续补充）

最初交付时 PDF 只能原样转交打印队列，仅当驱动本身支持 PDF 时才能出纸。本次补上了 PDF 渲染能力。

关于 MuPDF：评估后未采用，原因是许可证。MuPDF 采用 AGPL-3.0，一旦链接，整个项目必须以 AGPL 发布——需向所有用户交付完整源码，且必须保证用户能替换重链接。对内部 / 商业分发基本不可行，除非向 Artifex 单独购买商业授权。

PDFium 采用 MIT 许可证，与本项目完全兼容，因此选择 PDFium。

实现方式：运行时动态加载

设计决策理由
用 LoadLibrary 运行时加载EXE 不链接 PDFium，保持零依赖；不用 PDF 的部署完全不需要这个 DLL
用户可选安装缺失时应用照常启动，PDF 作业降级为原样转交队列，原因写入日志
用 FPDF_LoadMemDocument直接从内存加载，无需写临时文件
300 dpi 栅格化与激光打印机常用分辨率一致，页面比例与清晰度兼顾
多页 PDF → 多页作业每个文档页独立栅格化并独立打印

实测结果

本轮真实运行验证了 PDF 链路（非仅语法检查）：

七、已知限制（请一并评估）

限制说明与建议
PDF 需可选的 PDFium PDF 栅格化依赖运行时加载的 PDFium（MIT 许可）。缺失时 PDF 原样转交队列，仅驱动本身支持 PDF 时可出纸。已用 tools/fetch_pdfium.sh 一键安装
未实现完整 IPP / AirPrint mDNS 当前广播的是 _pdl-datastream._tcp。真正的 AirPrint 需要 IPP 服务器 + URF 支持，工程量较大，建议作为下一阶段
RENDER 模式无作业队列 渲染是同步进行的，大文件会占用连接线程。批量场景建议走 RAW 模式交给系统队列
mDNS 单实例 5353 端口被其他 mDNS 响应器（如 Bonjour）占用时，本程序无法加入组播。多数系统允许多进程共享，但需实测确认
未在 Windows 上编译 语法与类型层面已充分验证，但 MSVC 的 /W4 可能报出 MinGW 未覆盖的警告。建议编译后确认无新警告

八、建议的后续步骤

  1. 先编译：在 VS 的 x64 Native Tools 提示符里执行 build-windows10.cmd，确认无编译错误与新警告
  2. 用虚拟打印机验证：把「Microsoft Print to PDF」设为 RENDER 模式，试一张图片和一段长文本，确认排版与 1:1 尺寸正确
  3. 再上真机：切到目标喷墨机 / 标签机，出纸确认
  4. 验证 API：跑 tools/smoke_test.sh，再用手机浏览器试一张图片
  5. 观察日志：logs\printer-server.log 会记录每次作业的类型、页数与成败

本次升级在 Windows 上未实际编译运行，所有验证均为语法级与类型级检查，物理出纸需在你的环境中确认。 基线快照保留在 backup/src-v2.0.0/，如需回滚直接覆盖 src/ 即可。
