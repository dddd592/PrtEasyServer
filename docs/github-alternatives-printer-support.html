一、先厘清：当前项目「打印机覆盖」的技术天花板

通读 src/printer_server.cpp 的 PrintRaw() 后可以确认，PrtEasyServer 目前只有两条数据通路，且二者都不改变「字节透传」这一本质：

  • RAW 通路（默认）：StartDocPrinter(RAW) → WritePrinter，把 TCP 9100 收到的字节原样塞进打印队列。客户端必须自己产出 PCL / PostScript / 厂商 RAW 格式的字节流。
  • XPS 通路（自定义分支新增）：StartXpsPrintJob，走 Windows XPS 打印 API。覆盖面比 RAW 宽，但要求客户端提交的必须是完整 XPS/OpenXPS 包。

关键结论：服务端从不做渲染。打印机型号能否被支持，取决于「该机型的固件能否直接消化 RAW 字节流」。

打印机类别典型型号RAW 直通是否可用原因
PCL / PS 硬件激光机HP LaserJet 1020 / P1005、Canon LBP 2900/3000、Brother HL 可用 固件原生解释 PCL/PostScript，RAW 字节流即最终打印语言
喷墨 / 墨仓一体机Epson L3150、Canon PIXMA MG2541、HP DeskJet 不可用 只有 GDI/Raster 驱动，必须由驱动把页面渲染成位图，RAW 字节流无意义
标签机Zebra ZD220D / ZT411、Brother QL-820NWB、TSC TTP-244 不可用 需要 ZPL / TSPL 专有指令集，不是 PCL/PS
小票 / 热敏机Epson TM-T88、Star TSP650II、Generic ESC/POS 不可用 需要 ESC/POS 或 StarPRNT 指令集
Host-based 机（CAPT）Canon LBP 2900/3000 部分固件 边缘 PCL 可用但部分高级特性失效；纯 host-based 机必须位图渲染
绘图仪 / 3D 打印机AxiDraw、Flashforge 不可用 G-code / 矢量指令，需专用解析器
一句话诊断：PrtEasyServer 是「RAW 透传服务器」，不是「打印服务器」。它把「打印机型号支持」的责任完全推给了客户端——客户端必须装对应厂商驱动并生成 PCL/PS 字节流。因此它天然无法服务喷墨机、标签机、小票机，也天然无法服务 iOS / macOS（AirPrint 客户端产出的是 URF/Raster/PDF，不是 PCL）。
另一层限制：客户端平台。即便机型是 PCL 激光机，macOS 与 iOS 也没有「生成 PCL 字节流」的能力（AirPrint 走的是 URF/Raster 或 PDF）。PrtEasyServer 自带的 BAT 安装脚本是让客户端安装厂商驱动 + 建 TCP/IP 端口，本质仍是传统「有客户端驱动」的模型——这正是它避免了 SMB 共享的 0x0000011b 问题，但也把 macOS/手机用户排除在外。

二、结论：能「支持更多打印机」的三条技术路线

路线 A · 服务端渲染 + IPP/AirPrint（覆盖面最广，首选）

让服务器用本机打印驱动把 PDF / 图片渲染成位图或 PCL，再通过标准 IPP Everywhere / AirPrint 分发。客户端零驱动，手机、Mac、Linux、Windows 全部原生可打，且任何已在 Windows 安装驱动的打印机（喷墨、标签、小票）都能吃。

这条路线是本次调研中唯一能真正突破「打印机型号天花板」的思路——它把渲染责任从客户端搬到了服务端。

路线 B · 厂商专有指令集（覆盖某一类打印机，不是通用方案）

针对标签机 / 小票机，直接实现 ZPL、TSPL、ESC/POS、StarPRNT 指令集并暴露 REST API。支持面窄但很深，是 A 的补充而非替代。

路线 C · 硬件桥接（脱离 PC，独立运行）

ESP32-S3 等 MCU 做 USB Host，把打印机直接变成网络打印机（IPP / RAW / 专有协议）。成本低、断电即用，但渲染能力弱、支持的驱动有限。

1Windows-AirPrint-Bridge

把任意 Windows 打印机变成 AirPrint + IPP 打印服务，客户端零驱动。路线 A 的典型代表。

  • 用 PyMuPDF 服务端渲染 PDF，绕开 ShellExecute printto 在 Edge 为默认阅读器时的失效问题

  • 自研 HTTP/1.1 服务端处理 Expect: 100-continue 与 chunked 传输

五、给 PrtEasyServer 的升级路径建议

按「投入产出比」排序，建议分三步走，每一步都可以独立交付：

第 1 步 · 补齐协议宽度（低风险，立刻见效）

  • 增加 LPR/LPD（RFC 1179）监听：老式 Unix 客户端、多数硬件打印服务器都走它
  • 增加 IPP 最小实现：Windows 10/11 自带「Microsoft IPP Class Driver」，macOS/Linux 也能以 IPP 方式接入
  • 增加 mDNS / Bonjour 广播（_ipp._tcp、_printer._tcp、_pdl-datastream._tcp）与 SNMP 状态查询，让客户端「看得见」这台服务器
  • 参考 printcap 的协议清单，逐项对齐

第 2 步 · 引入服务端渲染（突破机型天花板的关键）

  • 新增打印模式：raw（保持兼容）/ xps（现有）/ render（新增）
  • render 模式流程：接收 PDF / 图片 → 按 IPP media 或作业参数设定 DEVMODE → 调用 StartDocPrinter(RAW) 并写入渲染后的位图流
  • 渲染后端可选：Win32 GDI（无需第三方库，但 PDF 解析要自己写）或引入 PDFium / MuPDF（覆盖 PDF 场景，效果最好）
  • 务必实现 1:1 物理尺寸 + 打印机原生 DPI 渲染，这是标签机打印被缩小的根因（参考 Windows-AirPrint-Bridge 的做法）
  • 打印选项（纸张、类型、彩色、双面）应从驱动动态读取，而不是硬编码，这样换打印机自动适配（参考 mfp-print-scan-server）

第 3 步 · 生态位扩张（按需）

  • ZPL / TSPL 指令集支持 → 打通 Zebra、Brother QL、TSC 标签机
  • ESC/POS / StarPRNT → 打通热敏小票机
  • AirScan (eSCL) → 把一体机变成网络扫描仪（mfp-print-scan-server 已完整实现，Windows 侧用 WIA）
  • REST / Web 管理台 → 打印作业审计、多打印机集中管理
选型时最容易踩的坑：A 组的 AirPrint 类项目（Windows-AirPrint-Bridge、ZPrint）虽然覆盖机型最广，但目前都是「共享一台打印机」——要么跟随 Windows 默认打印机，要么启动时 --printer 指定单台。而 PrtEasyServer 的核心卖点恰恰是多台打印机各自独立开端口、客户端用 IP:端口 区分。

如果要「支持更多打印机」同时保住多打印机并行，正确做法是：保留现有每打印机一个监听端口的架构，在每个端口上叠加 IPP/AirPrint 语义（而不是引入一个新的统一服务），并给每台打印机单独跑一个 mDNS 实例标识（不同 UUID 与 rp 记录）。这样既兼容现网客户端，又能吃到新客户端生态。
